# Hermes reviews on `hag` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Hermes on `hag` reviews the fan loop every 6 h from fixed analysis scripts, makes at most one threshold change per review through the loop's API, reports changes on Telegram, answers chat questions about the fans, and sends a daily summary.

**Architecture:** Three stdlib-only Python scripts and one shared module, deployed to `~/.hermes/scripts/` on `hag`. They are the only way Hermes touches the loop: they call its HTTP API (reads open, writes with the token), print compact pre-computed text, and keep a small state file and Hermes's notes. A Hermes skill, `fan-controller`, tells the model the rules and the script commands; two Hermes cron jobs run them (an agent review every 6 h whose pre-run script sends the start mark, and a no-agent daily summary). Ansible deploys the scripts, skill, settings, token and jobs; Hermes itself and its Telegram bot are set up by the user.

**Tech Stack:** Python ≥ 3.10, standard library only (`urllib.request`, `json`, `zoneinfo`, `statistics`), `unittest`. Hermes Agent v0.23.1 cron and skills. Ansible.

**Spec:** `docs/superpowers/specs/2026-11-12-gpu-fan-controller-design.md` (sections 5.6, 5.7, 5.9, 6, 8). Plan 1: `docs/superpowers/plans/2026-11-23-fan-loop.md`.

**Scope:** plan 2 of 2: spec section 6, the `hag` part of 5.10, and the "Hermes" tests in section 8. Nothing on t4 changes. Out of scope (spec 10): a systemd unit for llama-server, and migrating Hermes's `custom_providers:` entry.

## Facts this plan rests on (checked on `hag`, 2026-11-27, read-only)

- Hermes Agent **v0.23.1**, user `hermes`, home `/home/hermes`, gateway running, **no messaging platform connected yet** (no `TELEGRAM_*` keys). No cron jobs, no `~/.hermes/scripts/`.
- **Cron** (`website/docs/user-guide/features/cron.md` in the install):
  - `hermes cron create SCHEDULE PROMPT --name N --script F --skill S --deliver T --failure-deliver T --timezone Z --paused [--no-agent]`.
  - `--script` is a **file under `~/.hermes/scripts/`**. Without `--no-agent` it runs **before the agent**, outside the model, and its stdout is put into the prompt. A last stdout line `{"wakeAgent": false}` skips the agent. `.py` files run under Hermes's own Python (3.14.9, `-I`), with a **sanitized environment**.
  - With `--no-agent`, the script's stdout is the message, empty stdout sends nothing, and a non-zero exit sends an error notice.
  - **There is no post-run hook.** This answers the check in spec 5.7: the pre-run script sends the start mark, and the note script sends the end mark.
  - The agent's **final reply is the delivered message**. A reply containing `[SILENT]` isn't delivered. `[CRON_FAILURE]` alone on the first line marks the run failed.
  - Explicit `hermes cron run NAME` runs a job even while it's paused. Jobs live in `~/.hermes/cron/jobs.json`; don't edit it by hand.
  - Cron jobs get the toolsets `terminal`, `file`, `vision` and `skills` by default; Telegram chat gets the same four.
- **Approvals:** `mode: manual`, `cron_mode: deny`. `python3 -c` and `python3 <<` are flagged, and quoted arguments are masked before most checks. `python3 /path/script.py args` isn't flagged (spec 3).
- **Telegram** (`website/docs/user-guide/messaging/telegram.md`):
  - `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ALLOWED_USERS=<numeric user id>` in `~/.hermes/.env`, written by `hermes gateway setup` (Telegram).
  - With no allowlist, Hermes denies everyone. Unknown senders get a pairing code, which only the owner can approve.
  - A DM's chat id equals the user id. That is the same number as `vault_fan_tg_chat_id`.
- **Skills:** `~/.hermes/skills/<category>/<name>/SKILL.md`, with YAML frontmatter that needs at least `name` and `description`.
- `hag` has system Python 3.12.3. It **can't resolve `t4`**, but it reaches the loop at `http://<t4 address>:8780` (checked).
- The loop API (plan 1) is described in `fanloop/api.py`. These are the parts used here:
  - `GET /status`, `GET /summary?since=&until=` (it includes `qualifying_on_current`), `GET /episodes?since=&version=`, `GET /changes?since=`, `GET /events?since=&kinds=` and `GET /history?start=&end=`.

## Review Focus

1. **The loop can't be reached** (t4 down, port closed, timeout). Each script prints one line, e.g. `Can't reach the fan loop: timed out`, and exits 1. `fan_review.py` sends no mark and doesn't wake the agent with half data. *(Task 1 `test_unreachable_loop_is_one_line`, Task 3 `test_unreachable_loop_fails_the_run`.)*
2. **A write is rejected** (stale `from`, evidence gate, daily limit, a hard limit). `fan.py write` prints the loop's error and detail, then the current thresholds and version, and exits 2. The model then re-decides; it never reports a change that didn't happen. *(Task 4 `test_rejected_write_shows_reason_and_current_values`.)*
3. **The note comes after the mark is gone** (a review longer than 15 min: the loop timed the mark out, or a second start superseded it). The note is still saved, and the script says the review's end wasn't recorded. *(Task 4 `test_note_saved_even_when_mark_already_closed`.)*
4. **There is nothing to analyse yet** (a fresh install, no episodes since the last review, no qualifying episodes, a truncated list). The report says "none" or "not enough data" and never divides by zero. A truncated list says so. *(Task 2 `test_reports_with_no_episodes`, `test_compare_needs_qualifying_episodes`.)*
5. **The token file is missing or unreadable.** Reads still work. Writes and marks fail with `No write token at <path>`, without printing the path's contents. *(Task 1 `test_missing_token_only_blocks_writes`.)*

### Task 2: Analysis and report text

**Files:**
- Modify: `hermes/scripts/fanlib.py`, `tests/test_hermes.py`

**Interfaces:**
- Consumes: episode dicts as `GET /episodes` returns them (`fanloop/episodes.py` `Episode` fields), and `/history` samples (`ts`, `temp0`, `temp1`, `level`, …).
- Produces, in `fanlib`:
  - `SETTLE_MIN_S = 360`. `LOUD = ("high", "max")`.
  - `hotter_peak(ep) -> Optional[float]`: the highest value in `ep["peak_c"]`.
  - `qualifies(ep) -> bool`: `duration_s >= 360`, not `review_overlap`, `hold_level is None`. This mirrors the loop's evidence rule, for display only; the loop's count decides.
  - `dominant_level(ep) -> Optional[str]`: the level with the most seconds in `level_s`.
  - `settle_by_level(eps) -> Dict[str, dict]`: over qualifying episodes that have an inlet, grouped by dominant level, the hotter peak minus `inlet_mean`, as `{"n", "median", "min", "max"}` rounded to 0.1.
  - `version_stats(eps) -> dict`, with these keys:
    - `n`, `qualifying`, `busy_s`, `slowdown_s`;
    - `slowdown_per_h` (slowdown seconds per busy hour), `loud_share` (High plus Max seconds over all level seconds) and `changes_per_h`;
    - `inlet` as `(min, max)` or None, `duration` as `(min, max)` or None.

    Zero busy time gives 0 rates, never a division by zero.
  - `compare(a: dict, b: dict) -> str`, where `a` and `b` are `version_stats` results, gives one of `"better"`, `"worse"`, `"same"` or `"not enough data"` for b against a.
    - If either side has `qualifying == 0`: `"not enough data"`.
    - Otherwise apply the spec 6.2 order: `slowdown_per_h` first (any difference > 1 s/h decides), then `loud_share` (a difference > 0.05), then `changes_per_h` (a difference > 0.5).
  - `step_response(samples, at: float) -> Optional[dict]`: the hotter card's temperature at the sample nearest `at` and nearest `at + 180`, as `{"temp_at", "temp_after", "delta"}`; None without samples on both sides.
  - `fmt_time(ts: float, tz_name: str) -> str` (`%a %H:%M` in that zone).
  - `review_report(status, summary, eps_since, eps_current, changes, level_events, steps, notes, since, now) -> str`.
  - `daily_report(status, summary, changes, now) -> str`.

**What `review_report` prints, in this order, as plain lines** (compact, well under 20k tokens):
1. `Now: <level> (<reason>), cards <t0>/<t1>°C, inlet <x>°C, thresholds v<N>: Low <l>, Medium <m>, High <h>, margin <g>, hold <s> s, ambient <rules or none>`.
2. `Problems: none`, or the false values in `status["health"]` and a `store_error` if present.
3. `Since last review (<fmt_time(since)>): <n> episodes, <busy> min busy, slowdown <s> s, peak <p>°C, inlet <a>–<b>°C`, or `Since last review (…): no episodes`. Then `(list truncated)` if the episodes list was cut.
4. `On v<N>: <qualifying> qualifying episodes (loop's count: <summary.qualifying_on_current>; a quieter review change needs 3)`, followed by the `version_stats` line for the current version.
5. `Settles above inlet (qualifying episodes): Medium +60.2°C (n 4, 58.1–61.0)` per level, or `not enough data`.
6. `After step-ups:` one line per step (at most 5, the newest): `Fri 14:05 low→medium: 63.0→66.5°C over 3 min`.
7. `Changes since last review:` one line per version (`v7 → v8 review: step_up.medium 65 → 63 (reason)`), or `none`. Then `Review changes in the last 24 h: <k> of 2; user-chat: <j> of 6`.
8. `Your last notes:` the last 3 notes (`<when>: <text>`), or `none yet`.

`daily_report` prints:
- `Fans, last 24 h: <n> episodes, <busy> min busy, time at Low/Medium/High/Max <a>/<b>/<c>/<d> min, slowdown <s> s, peak <p>°C, max inlet <i>°C.`
- `Now: <level>, cards <t0>/<t1>°C, inlet <x>°C, thresholds v<N>.`
- One `Changed:` line per version in the last 24 h, or `No threshold changes.`
- A `Problems:` line only if there are problems.

### Task 3: `fan_review.py`, the review's pre-run script

**Files:**
- Create: `hermes/scripts/fan_review.py`
- Modify: `tests/test_hermes.py`

**Interfaces:**
- Consumes: `fanlib.load_settings`, `Loop`, `State`, `review_report`, `step_response`.
- Produces: `main(argv=None, settings_path=fanlib.DEFAULT_SETTINGS, now=None) -> int`. It prints the report and returns 0, or prints one line and returns 1.

**Behaviour:**
1. **First**, `POST /marks/start`, before any read (spec 5.7). Save `mark_id` and `last_review_started_at = now` in state.
2. `since` = state `last_review_at`, or `now - 86400` if there's none. `last_review_at` is set to `now` only at the end of a successful run.
3. Read these:
   - `/status` and `/summary?since=<since>`;
   - `/episodes?since=<since>` and `/episodes?version=<current>`;
   - `/changes?since=<now-86400>` (the 24 h counts are computed from it; the report shows the versions since `since`);
   - `/events?since=<since>&kinds=level`.

   For each step-up level event (`to` louder than `from`, at most the 5 newest), read `/history?start=<ts-30>&end=<ts+210>` and pass it to `step_response`.
4. Print `review_report(…)` and the last 3 notes. Return 0.
5. If the start mark fails, print the error and return 1, so Hermes records the run as failed and the agent doesn't run.

   If a read fails after the mark started, print `Review data incomplete: <error>` and `{"wakeAgent": false}` as the last line, then return 1. The loop times the mark out after 15 min, which counts as a failed review (spec 5.7).

### Task 4: `fan.py`, the model's commands

**Files:**
- Create: `hermes/scripts/fan.py`
- Modify: `tests/test_hermes.py`

**Interfaces:**
- Consumes: Tasks 1–2.
- Produces: `main(argv, settings_path=fanlib.DEFAULT_SETTINGS, now=None) -> int`, an `argparse` CLI with these subcommands:

| Command | Does | Exit |
|---|---|---|
| `status` | line 1 and 2 of the review report (now, problems) | 0 / 1 |
| `episodes [--days N]` (default 7) | `version_stats` and `settle_by_level` over that window | 0 / 1 |
| `compare A B` | `version_stats` of each version's episodes, side by side, and `compare` verdict for B vs A | 0 / 1 |
| `changes [--days N]` (default 7) | one line per version, as in the report | 0 / 1 |
| `write --source {review,user-chat} --reason TEXT PARAM FROM TO [PARAM FROM TO …]` | `POST /thresholds` with those changes, applied together or not at all | 0 ok / 2 rejected / 1 error |
| `note FILE` | saves FILE's text as a note, ends the open mark | 0 / 1 |

**`write` values:**
- The positional arguments come in triples; a count that isn't a multiple of 3 prints `Bad value: …` and exits 1. A `review` write with more than one triple is still sent: the loop rejects it (`review-multi`), and the loop's rule is the one that counts.
- For `step_up.*`, `margin` and `hold_s`, FROM and TO are numbers.
- For `ambient.add` FROM is `none`; for `ambient.remove` TO is `none`.
- A rule is written `INLET:LEVEL`, e.g. `30:high`, and becomes `{"inlet_min": 30, "level": "high"}`.
- A value that doesn't parse prints `Bad value: …` and exits 1, without calling the loop.

**`write` output:**
- On success: `Applied: v<old> → v<new>: <param> <from> → <to>`, with `, ` between several changes. The loop's own bot announces it as well (spec 5.9).
- On a 409:
  - `Rejected (<error>): <detail>`;
  - `Current thresholds v<N>: …` (line 1's threshold part);
  - `Nothing was changed. Read the values above and decide again.`

**`note FILE`:**
- Reads FILE (UTF-8, at most 4000 characters). It appends `{"at": now, "mark_id": state.mark_id, "text": …}` to `notes.jsonl`, then sends `POST /marks/end {id: mark_id}`.
- If `{ended: true}`, it prints `Note saved; review end recorded`, sets `last_review_at = state["last_review_started_at"]` and deletes FILE.
- If `ended` is false, or there was no open mark, it prints `Note saved; the loop had already closed this review (over 15 min or superseded)` and returns 0 anyway, because the note matters more.
- A note never deletes anything but FILE.

**Files:**

**`SKILL.md`** has frontmatter `name: fan-controller` and a `description` that names t4's fans, GPU temperatures, thresholds and fan reviews, so it also loads in chat. The body is at most about 120 lines, with these sections:
1. **What this is:** two sentences (spec 1 and 4). The loop decides in real time; you review, tune and report.
2. **Commands:** every `fan.py` subcommand, written exactly as `python3 /home/hermes/.hermes/scripts/fan.py …`, with an example of each. Never use `python3 -c`, heredocs or pipes.
3. **Rules for numbers:** use only numbers printed by these commands or by the review data above; never compute or remember them yourself.
4. **A scheduled review** (spec 6.2):
   - The data is already in your prompt.
   - Decide whether **at most one** change is justified. Prefer the safer, louder direction when a slowdown happened.
   - A quieter change needs 3 qualifying episodes on the current version; the loop enforces it.
   - Judge your last change with `compare <old> <new>`. If it's `worse`, revert it as one change.
   - The order of "better": no thermal slowdown, then less time at High and Max, then fewer level changes.
   - For anything outside measured inlets, say it's an extrapolation (spec 6.3).
5. **Writing a change:**
   - `write --source review` with the current value as FROM.
   - Keep `--reason` short, without quotes or apostrophes; this is the reason text the loop announces.
   - If it's rejected, read the printed current values and decide again; the loop doesn't allow a second try with the same value. Never say a change was made unless `Applied:` was printed.
6. **The note:**
   - Write it with the file tool to `/home/hermes/fan-controller/note.md`, then run `fan.py note /home/hermes/fan-controller/note.md`. This must be the last command of every review, even one with no change.
   - Format: `What:`, `Why:`, `Evidence:`, `Check next time:`.
7. **The message** (your final reply is delivered to Telegram):
   - After a change or a revert:
     - what changed (`Medium 65 → 63°C, v7 → v8`), and why;
     - the evidence from the data, e.g. `based on 4 episodes on v7 (6–22 min, inlet 12–15°C)`;
     - what you'll check next.
   - Also for a rejected write you couldn't resolve, a slowdown in the data, or a prediction that Max won't be enough.
   - Otherwise reply `[SILENT]` (*my call*: the daily summary covers quiet periods, so 4 "no change" messages a day aren't needed).
   - If the data couldn't be read or the note failed, start the reply with `[CRON_FAILURE]` alone on line 1.
8. **In chat:**
   - "How hot is it now": `fan.py status`. "What changed this week": `fan.py changes --days 7`.
   - A change the user asks for: `write --source user-chat`, with `--reason` quoting what they asked for. Values that only work together, such as moving Medium and Low because of the 3°C gap, go in one write as several triples. At most 6 such writes a day.
   - Chat is never marked, and needs no note.
   - Never put tokens or addresses in a reply.
